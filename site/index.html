C++20 · Raft · linearizable key-value store

quorumkv

A key-value store that stays correct when machines crash, networks split and messages arrive late, twice, or not at all. Five copies agree on every write through the Raft consensus protocol.

The cluster on this page runs a small JavaScript model of the same protocol. Crash the leader and watch the others elect a new one. Split the network and watch the minority side stop accepting writes. A safety check runs on every step, like the one in the project's simulator.

    02 · Proof the checks work

    Bugs planted on purpose

    Each check was first shown to catch a deliberately broken variant. The seed is the first simulated run that exposes it.

    Injected defectCaught byFirst seed

    Real bugs found during development

    • The server's event loop accepted new connections before reading every polled entry, and read past the end of its poll list. The three-server TCP test crashed on it.
    • The checker's counterexample shrinking cut the history at the wrong operation, and later removed writes that remaining reads had observed.
    • On Windows the journal file was opened without write sharing, so reopening a data directory failed.
    • An early replication sender waited for an acknowledgement before sending the next batch.
    03 · Performance

    Measured, with the caveats

    Release build, 32 closed-loop clients, each configuration run 5 times. Bars are medians, whiskers span min to max. All nodes share one machine, so this measures one CPU and one disk, not a network. Differences under about 20% are noise.

    04 · Design

    One Raft core, two worlds

    The protocol code never touches sockets, threads or clocks. It only sees four interfaces, so the simulator tests the exact code that serves clients.

    ReadIndex instead of leases

    A read costs one heartbeat round and stays correct with any clock drift. Reading the leader's memory directly is not linearizable, and the checker proves it.

    Sessions in the state machine

    Every replica and every snapshot carries each client's last sequence number and reply, so a retry is recognized by whichever node leads next.

    An append-only journal

    Each batch is one checksummed record and one fsync. A torn final record is detected and dropped on restart, and the log is compacted into an image now and then.

    Per-link TCP proxies for faults

    Blocking one proxy cuts exactly one direction of one link, with no root access and no firewall rules.

    05 · Limits

    What it does not do

    One machine

    Every benchmark runs on localhost. Threads are not pinned and turbo boost is not disabled.

    Fixed membership

    No adding or removing nodes, no sharding, transactions or TLS.

    State fits in memory

    The store is an in-memory map, and snapshots serialize all of it, within a 64 MiB image limit.

    Disk-bound writes

    Every batch waits for an fsync on the leader and on a majority of followers.
